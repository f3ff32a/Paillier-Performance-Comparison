# GPU 并行化实现说明

本实现以用户提供论文的消息独立性、承诺矩阵行独立性和 8 位桶分解为依据，扩展上传的 v6 CPU 实现。大整数计算采用 NVIDIA CGBN，CPU 工作者继续使用 GMP，NTL 数据转换保留在调用线程。

## Commit 的计算分解

每一行仍计算

\[
C_i=g^{\rho_i}\prod_{j=0}^{v-1}g_j^{M_{i,j}}\pmod Q.
\]

将随机项视为最后一个生成元/指数对 `(g,rho_i)`，与其他列一起处理。对指数按字节展开，令 `digit(i,j,w)` 为第 w 个 8 位窗口：

\[
R_{i,w}=\prod_j b_j^{\operatorname{digit}(i,j,w)}\pmod Q.
\]

GPU 的一个 32 线程 CGBN 协作组计算一个 `(i,w)`。它在独占的 256 个桶中累乘生成元，随后从 255 到 1 计算后缀积及其乘积。各组的桶互不重叠，不使用会争抢同一个大整数的原子模乘。

窗口结果保留在设备内存。第二个内核为每一行执行高位到低位的 Horner 合并：`acc = acc^256 * R[i,w] mod Q`，每窗只需 8 次平方。只将最终的每行承诺拷回 CPU。整个计算始终处于 Montgomery 表示，最终转换回普通整数。

`Q`、Montgomery 单位元和生成元在一次矩阵 Commit 调用的 CUDA 会话内复用。矩阵指数按领取的行批次打包，桶缓冲进一步按窗口任务分块，因此无需同时分配“全部行 × 全部窗口 × 256 桶”。显式缓冲区大小受 `ZKP_GPU_MEMORY_MIB` 和当前可用显存限制。

这种分解与逐列完整模幂的结果一致，并保留论文的桶方法。较短矩阵仍能通过窗口维度产生多个 GPU 任务。不过桶访问模式、存储补齐和设备带宽会影响真实速度，需要实测。

## Montgomery 表示和位宽

GPU 使用 32 位无符号 limb，最低有效 limb 在前。主机打包先检查符号与位宽，超出范围会报错，绝不截断。模数要求奇数且大于 1。

这里有一个 CGBN 特有的细节：32 个线程组成的环境会补齐每线程 limb 数。Montgomery 基数对应的是内部完整位宽：

\[
B_R=1024\left\lceil B_{storage}/1024\right\rceil,\qquad R=2^{B_R}.
\]

例如 256/512 位存储使用 `R=2^1024`，1536 位存储使用 `R=2^2048`。这是 CGBN `impl_cuda.cu` 的 `bn2mont` 实现所规定的行为，不能直接使用 `R=2^B_storage`。`GmpSupport.hpp` 中的 `montgomeryRadixBits` 与此对应，主机模型测试覆盖这些情况。

主机计算 `R mod Q` 和 `base*R mod Q`，内核使用 `np0=-Q[0]^{-1} mod 2^32` 做 Montgomery 模乘。所有承诺值和最终密文都转换回原有的整数表示。

## Paillier 批量加密

随机数 `Rm[i]` 沿用 v6，在主线程按原顺序生成。GPU 批次接收相同的消息和随机数。主机用 GMP 计算较轻的 `(1+n*m) mod n²` 及 Montgomery 编码；GPU 的每个协作组用 4 位固定窗口计算 `r^n mod n²`，再完成最终模乘。

CPU/GPU 的协作单位是完整的一条普通消息密文。`CRj`、`Cm_`、`calculateLj`、`wireUp`、`run`、挑战生成和验证代码的执行顺序没有重排，也没有在 GPU 内生成随机数。

## 共享队列与错误处理

GPU 首批任务在 CPU 工作者启动前预留，避免设备初始化期间 CPU 把所有任务领走。之后 CPU 每次领取一项，GPU 根据最近一次完整批次的实际耗时调整领取数量。没有将每个消息集合切为必须共同结束的固定轮次；CPU 可在 GPU 运行时继续领取工作。

默认每次矩阵/批量调用重新估计 GPU 批量，不保留跨阶段速度状态。该策略是基于耗时的自适应批量与动态领取，不是 CPU/GPU 全局最优负载求解器。尾部仍可能等待一个已经领走的 GPU 批次；`--gpu-max-chunk` 可限制该影响。

工作线程只读主线程准备的字符串和公共 GMP 参数，写入不同输出索引。输出容器在启动前分配完毕。线程在全部任务完成后统一退出，主线程才把结果转回 NTL，因此不共享可变 NTL 模数上下文。

`auto/hybrid` 中若 CUDA 失败，已领取的整个批次由 CPU 用同一输入重新计算，包括可能已部分写回的位置；此调用剩余任务继续在 CPU 执行。`cuda` 模式保留错误并失败。CPU 异常也会传回调用线程。启用 `--verify-gpu` 时，GPU/CPU 数值不一致在所有模式下均为致命错误。

## 与原论文的关系及边界

本实现将原“行间并行”进一步分为“行间任务队列 + GPU 行内窗口并行”。承诺式、密文式、随机值的来源、生成元、交互/挑战顺序与证明格式保持原版本语义。单向量承诺和验证端计算仍使用原 CPU 实现。

证明记录的函数等价与实现的运行时安全审计是不同验证层面。固定随机输入的 v6/新 CPU 记录对照已完成；GPU 记录一致性的实机测试已提供但当前环境未执行。没有从 CPU 论文的 3.1–4.2 倍结果推断 GPU 加速比。

本次参考用户上传论文的 III-A、III-B 和 IV 节。CGBN API 及内部实现来自 [NVIDIA CGBN](https://github.com/NVlabs/CGBN)，CUDA 调用语义参考 [NVIDIA CUDA Programming Guide](https://docs.nvidia.com/cuda/cuda-c-programming-guide/)。主机传输使用普通内存，可能阻塞 GPU 管理线程；CPU 工作者独立运行，本实现不宣称已经实现 H2D/内核/D2H 流水重叠。
